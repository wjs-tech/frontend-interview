## 1. Tree Shaking 摇掉的是"没被用到的导出"，不是你写错的逻辑（⭐️）

**一句话结论**：Tree Shaking 在构建时顺着 ES Module 的 import/export 图，从入口出发把"谁也没引用"的代码整段删掉；它是基于静态结构的可达性分析，不是运行时魔法，也不是压缩。

🍳 **生活类比**：备宴席前先列菜单，只买要做的菜。你 `import` 了 `add`，bundler 就把同文件里没人用的 `subtract`、`multiply` 当成"没进菜单的食材"留在仓库、不装进外卖盒。

🔍 **原理下沉**：
- 关键是"静态"。ESM 的 import/export 写在文件顶层、名字编译前就确定，bundler（Vite 用 Rollup、webpack5 用 `optimization.usedExports`）能不执行代码就画出整张依赖图，从入口标出"可达"的节点，没被标到的 export 直接丢弃。
- 反例是 CommonJS：`require()` 是函数调用，可以写在 `if` 里、可以拼路径，bundler 没法在构建期证明某个导出没被用，只能整包保留。所以 `lodash`（CJS 版）`import _ from 'lodash'` 会把整库打进去；换成 `lodash-es` 按需 named import 才摇得动。
- `sideEffects` 字段是给 bundler 的"安全声明"：package.json 里写 `"sideEffects": false`，等于说"这个包任何文件被引进来、只要没用到它的导出，整体都能丢"。但如果你的包顶层有副作用（比如 `import './polyfill'` 改了 `Array.prototype`、或者 import 了 css），写成 false 会在生产环境把这段悄悄删掉——dev 不严格反而发现不了，上线才炸。有副作用的文件用数组白名单 `"sideEffects": ["*.css", "./polyfill.js"]` 兜住。
- 它和 minification 是两件事：Tree Shaking 决定"哪些代码存在"，minify（Terser/esbuild）决定"留下的代码怎么压成最小"（重命名、去注释空格）。先摇后压，流水线上下游。

🔁 **对比学习（写法层面，决定能不能摇）**：
```js
import { debounce } from 'lodash-es'        // ✅ 摇得动
import _ from 'lodash'                       // ❌ 整包进
import * as utils from './utils'             // ❌ 后面 utils[name] 动态取，bundler 不知道你取哪个，只能全留
```
深层的 `export * from './x'` barrel 文件，好 bundler 能摇，但嵌套太深有时会拖进多余代码；能写 subpath（`import x from 'lib/button'`）就用 subpath。

💥 **我踩过的坑**：早年 Vue2 项目接 moment.js，日期格式化随手 `import moment from 'moment'`，打包出来光这一个库就几十 KB 全进主包，还是 CJS 摇不动；后来换成 dayjs / date-fns 的 ESM 按需才下来。另一个更隐蔽的：给某个自己写的组件库设了 `"sideEffects": false`，结果组件里 `import './style.css'` 被当成可丢弃副作用，生产环境样式没了——dev 好好的，提测才暴露。

🎯 **面试官可能追问**：Tree Shaking 和 minification 区别？为什么 CJS 摇不动？`sideEffects: false` 写错了会怎样？barrel 文件为什么有时会让包变大？

## 2. Code Splitting：把"一整桌菜"拆成"按桌下单"（⭐️）

**一句话结论**：Code Splitting 是把一个大 bundle 拆成多个按需加载的小 chunk，首屏只下载当前要用的那块，剩下的等用户真走到那条路由、点到那个组件再去拉；核心是动态 `import()`。

🍳 **生活类比**：宴席不分餐，所有人来了先把满汉全席全端上桌——前菜没动、主菜凉了、客人还在等。分包像分餐制：先上你这桌要吃的，别的桌的菜等他们入座再上。

🔍 **原理下沉**：
- 静态 `import` 一定进主包；一旦写成动态 `import()`（返回 Promise），bundler 就在那个调用点切一刀，单独产出一个 chunk 文件（如 `312.abc1d2.js`），运行时第一次执行到这行才发请求去 fetch。
- 最常见的两种拆法：**路由级**（每页一个 chunk，用户没去的页不下载）和**组件级**（富文本编辑器、图表、PDF 预览这种重组件，等它真的要显示了再加载）。
- **vendor 分离**：把 `node_modules` 里变化少的第三方代码（React/Vue 本身）单独打一个 chunk，应用代码频繁改、vendor 长缓存，二次访问省流量。webpack 用 `splitChunks`，Vite 用 `build.rollupOptions.output.manualChunks`。
- **预取**：`webpackPrefetch` / `webpackPreload` 魔法注释让浏览器空闲时提前拉"下一步可能用的"chunk，掩盖网络延迟；但别贪，过度 prefetch 浪费带宽。
- **过度拆分的反作用**：拆出 50 个 5KB 的小 chunk，HTTP 请求开销反而拖慢——经验上 30–40KB 以下的代码不值得单独成块。先拿 bundle analyzer 看数据再拆，别凭直觉。

🔁 **对比学习（路由懒加载，Vue 和 React 并排）**：
```jsx
// React（v18 + react-router v6）
import { lazy, Suspense } from 'react'
const Dashboard = lazy(() => import('./pages/Dashboard'))   // 这一步才切出 chunk
function App() {
  return <Suspense fallback={<Loading/>}><Dashboard/></Suspense>
}
```
```js
// Vue3 + Vue Router：函数式 component 直接写动态 import
const routes = [
  { path: '/dashboard', component: () => import('./views/Dashboard.vue') },
]
// 组件级也可用 defineAsyncComponent(() => import('./X.vue'))
```
两者底层都是动态 `import()`，只是包裹方式不同：React 要 `<Suspense>` 当加载态容器，Vue 在路由层或 `defineAsyncComponent` 里自带 loading。

💥 **我踩过的坑**：用 `React.lazy` 忘了包 `Suspense`，运行时直接报错。更狠的是——只包了 Suspense 没收错误边界：某次部署中途用户正在导航，新 chunk 还没传完、旧 chunk 404，`Suspense` 管不了"加载失败"，错误一路向上把整页干崩成白屏。后来老老实实加了 Error Boundary 兜住 chunk load failure。还有一次没拆 vendor，首屏把 React + 一堆库全塞主包，LCP 很难看。

🎯 **面试官可能追问**：Tree Shaking 和 Code Splitting 什么关系（一个删死代码、一个拆活代码，协同）？lazy 没包 Suspense 会怎样？chunk 加载失败怎么兜底？拆太细有什么代价？

---

Tree Shaking 解决"包里有没用的"，Code Splitting 解决"有用的别一次性全给"。两个都是同一句话：**别让用户的带宽替你的疏忽买单**。
