## 无限滚动列表（虚拟列表）⭐️⭐️⭐️

> 需求：后端一次性返回 10 万条数据，页面要能流畅滚动、不卡死。直接 `v-for` 怼 10 万个 DOM 节点？我第一次这么干的时候，页面直接冻了三秒，滚动像看幻灯片。

### 一句话结论

别把 10 万个节点都塞进 DOM。**只渲染视口里能看到的那一小撮**（加上下各缓冲几条），滚动时动态替换内容。这就是虚拟列表，核心就一句：DOM 节点数量 ≈ 你能看到的条数，和数据总量无关。

### 🍳 生活类比：图书馆只摆你眼前的书

想象一个 10 万册的书库。真要开馆，你不可能把 10 万本书全摊在阅览桌上——桌子早塌了，读者也找不到。

真实图书馆怎么干？书都在地下书库，阅览区只摆你当前楼层、当前书架能看到的几十本。你往前走两步，管理员就把身后那排收走、把前面那排补上来。你始终只面对几十本，但"感觉"自己逛完了整个书库。

虚拟列表就是那个管理员：**数据全在内存（书库），DOM 只留视口内（阅览桌），滚动 = 换批次上架。**

### 🔍 原理下沉

三个数就够了：

- `startIndex`：当前视口第一条该渲染的数据下标；
- `endIndex`：视口最后一条；
- `offset`：上面那些"没渲染"的条目撑起来的总高度，用一个占位元素（或 `paddingTop`）顶住，让滚动条比例真实。

基础版（定高）公式：

```js
const itemHeight = 40        // 每条固定 40px
const visibleCount = Math.ceil(containerHeight / itemHeight) // 视口能塞几条
const startIndex = Math.floor(scrollTop / itemHeight)
const endIndex = startIndex + visibleCount + buffer // buffer 是上下缓冲，防白屏
```

不定高（真实业务里更多）就麻烦了：你不知道 `scrollTop` 对应第几条。常见两种路：
1. **预估高度 + 测量后修正**：先按估的渲染，渲染完用 `ResizeObserver` 量真实高度，回填位置缓存，滚动时二分查找；
2. **直接上 `ResizeObserver` + 动态 offset 数组**：维护一个前缀和数组，每次高度变了就更新。工程里我一般懒得自己写，直接 `vue-virtual-scroller` / `react-window` 一把梭。

### 🔁 对比学习（Vue3 / React）

写法上两边思路一样，差异在响应式 API：

**Vue3 写法（我熟）**：`scrollTop` 放 `ref`，`computed` 算 `visibleList`：

```vue
<script setup>
import { ref, computed } from 'vue'
const list = ref(/* 10 万条 */)
const scrollTop = ref(0)
const containerH = 400
const itemH = 40
const buffer = 5
const visible = computed(() => {
  const start = Math.max(0, Math.floor(scrollTop.value / itemH) - buffer)
  const end = start + Math.ceil(containerH / itemH) + buffer * 2
  return list.value.slice(start, end).map((item, i) => ({ ...item, _i: start + i }))
})
</script>

<template>
  <div class="viewport" :style="{height: containerH+'px', overflow:'auto'}"
       @scroll="scrollTop = $event.target.scrollTop">
    <div :style="{ height: list.length * itemH + 'px', position:'relative' }">
      <div v-for="row in visible" :key="row._i"
           :style="{ position:'absolute', top: row._i * itemH + 'px', height: itemH+'px' }">
        {{ row.name }}
      </div>
    </div>
  </div>
</template>
```

**React 写法（我在补）**：`scrollTop` 放 `useState`，用 `useMemo` 算可见区间，其余几乎同构。React 这边我更倾向直接上 `react-window`，它的 `FixedSizeList` 把测量和回收都封装好了，自己写 `onScroll` 算 index 容易踩 `key` 的坑：

```jsx
import { FixedSizeList } from 'react-window'
<FixedSizeList height={400} itemCount={100000} itemSize={40} width="100%">
  {({ index, style }) => <div style={style}>第 {index} 条</div>}
</FixedSizeList>
```

> 升级观：Vue3 的 `computed` 自动依赖追踪，比 React 手动管 `state` + `useMemo` 依赖数组省心；但 React 生态的虚拟列表库（`react-window` / `react-virtualized`）成熟度高，不定高场景直接拿来用更稳。

> 📌 2026 现状补充：React 这边现在新项目更流行 **TanStack Virtual**（`useVirtualizer` headless hook，框架无关，不定高用 `measureElement` 自动 `ResizeObserver` 测量）。`react-window` 的 `FixedSizeList` 写法（上面那段）是 v1 API，仍大量在用、很好懂，但要注意 v2 已破坏性重写、旧的 `FixedSizeList` 教程不全适用了。定高简单列表 `react-window` 一把梭足够；要 headless 控制力（sticky、横向、复杂 range）再上 TanStack。Vue 这边我仍首推 `vue-virtual-scroller`，自己写定高版也就几十行。

### 💥 我踩过的坑

1. **滚动太快白屏**：一开始没加 `buffer` 缓冲，快速滚动时新节点还没渲染出来，视口空了一下。后来上下各多渲染 5 条就稳了。
2. **`key` 用数据 id 还是下标？** 定高版用 `_i` 下标当 key 没问题；但如果你在列表里做"删除/插入"，下标 key 会错位。我现在一律优先用数据自身稳定 id 当 key。
3. **不定高硬上定高公式**：有次后端返的卡片高度参差，我偷懒按 40px 算，结果长内容被截断、短内容大片空白。不定高就老实上测量方案，别省。
4. **`@scroll` 不节流**：早期没想那么多，其实现代浏览器滚动事件本身就合并帧了，Vue/React 的批量更新也兜了一层，一般不用手动 `requestAnimationFrame` 包。但如果你在 `scroll` 里做重计算，还是建议 rAF 收一下。

### 🎯 面试官可能追问

- 不定高怎么处理？（答预估 + `ResizeObserver` 修正 / 前缀和数组）
- 十万条之外还要"下拉加载更多"怎么接？（虚拟列表管渲染，分页/无限加载管数据，两层解耦）
- 横向虚拟列表呢？（思路一致，把高度换成宽度）
- 为什么不直接用 `content-visibility: auto`？（它是 CSS 原生懒渲染，对"已知总数"的列表有效且零 JS，但对需要精确滚动定位/频繁增删的场景，还是虚拟列表可控）

> 我不确定之处：`content-visibility` 在超长列表的实际收益边界，以及和 IntersectionObserver 自己实现的懒渲染谁更省，我还没在真实大项目里 AB 过，上面是理论判断。

## 前端组件库设计思路 ⭐️⭐️⭐️

> 需求：团队 10 个人都在写业务，按钮样式一周出 8 个版本、表单校验各写各的。老板说"搞个组件库统一一下"。我第一反应是：组件库不是把代码堆一起，是想清楚"哪些该抽、接口怎么定、样式怎么不打架"。

### 一句话结论

组件库的本质不是"写了多少组件"，而是**定了一套别人愿意遵守的约定**：统一的 API 风格、样式隔离与主题机制、按需加载、类型约束、可访问性底线。先想清楚边界（哪些进库、哪些留给业务组合），再动手写第一个 `<Button>`。

### 🍳 生活类比：连锁餐厅的中央厨房

一家连锁餐厅，每家门店（业务线）都自己切土豆、调酱料，味道肯定飘。

正解是中央厨房：把"标准化半成品"备好——腌好的肉、统一的酱包、规定好的火候。门店只要按 SOP 组装，出餐快、味道稳。但中央厨房**不替门店决定"今天卖什么套餐"**，那部分留给门店自己组合（业务组件）。

组件库就是那个中央厨房：提供稳定、一致、可组合的"半成品零件"；业务页面是门店，用这些零件拼自己的套餐。**库管"零件长什么样、怎么接"，不管"你拿它炒什么菜"。**

### 🔍 原理下沉：设计维度拆解

真要落地一个库，我会盯这 6 个维度：

1. **API 设计（最容易被低估）**
   - 用 `props` 传配置、`events`/`v-model`/`update:xxx` 出结果、`slots` 留灵活内容区；
   - 配置项**分组不堆砌**：一个组件 props 超过七八个就考虑拆子组件或用 `object` 收一下；
   - 给默认值、留 `size`/`type`/`disabled` 这类通用字段约定，让所有组件"长得像一家人"。

2. **样式隔离与主题**
   - Vue 我用 `scoped` + **CSS 变量**（`--my-color-primary`）做主题，换肤只改根节点变量；
   - 主题定制两条路：轻量 = CSS 变量覆盖（亮/暗色切换零成本）；深度 = 暴露 SASS/LESS 变量在构建期覆盖（Element Plus / Ant Design Vue 都这么干，配 `unplugin-vue-components` 的 resolver）；
   - 避免 `!important` 打架，命名上 BEM 或加统一前缀。

3. **按需加载（关系首屏体积）**
   - 绝不在入口 `import 'xxx/dist/index.css'` 全量引；
   - Vue3 用 `unplugin-vue-components` + 对应 resolver（`ElementPlusResolver` / `NaiveUiResolver`），模板里直接写组件名，插件自动只引入用到的 JS + 样式；
   - React 这边看库，`antd` 走 `babel-plugin-import` 或 `Vite` 的 `transfrom` 按需，新项目多用 ESM 原生 tree-shaking。

4. **TypeScript 类型**
   - props 全量类型化，泛型组件（`Table<T>`）该给就给；
   - 对外暴露的 `props` 类型 + `emit` 类型 = 组件的自说明文档，省一半沟通成本。

5. **可访问性（a11y）底线**
   - 按钮有 `aria-label`、弹层焦点管理、`role` 别乱加；
   - 这块我做得一般，但面试时能说出来"我知道这是底线、至少保证键盘可操作"就加分。

6. **文档与 Demo**
   - 没有文档的组件库 = 没人用。每个组件配"什么时候用 / 怎么用 / 有哪些坑"；
   - 我自己的库习惯每个组件一个 `.md` + 一个可运行 Demo，比纯注释强十倍。

### 🔁 对比学习（Vue / React）

两边哲学不同：

**Vue（我熟，5 年实战）**：组合靠 `props` + `slots`，样式 `scoped` 天然隔离，组件库写出来"模板感"强、上手快。`<MyTable><template #toolbar>...</template></MyTable>` 这种具名插槽留扩展位特别顺。

```vue
<!-- 业务里用我的组件库，只装零件不操心样式 -->
<MyButton type="primary" :loading="submitting" @click="onSubmit">保存</MyButton>
<MyTable :data="list" :columns="cols">
  <template #actions="{ row }">
    <MyButton size="small" @click="edit(row)">编辑</MyButton>
  </template>
</MyTable>
```

**React（我在补）**：没有 `slots`，扩展位靠 `children` / `render props` / 组合组件（`<Table><Column/></Table>`）；样式更早拥抱 CSS-in-JS（`styled-components`）或 CSS 变量。React 组件库（如 Ant Design）大量用 `context` 下发表单/主题状态，这一点比 Vue 的 `provide/inject` 用得重。

> 升级观：Vue 的 `scoped` + `slots` 让我写业务组件库时"样式不漏、扩展位清晰"，心智负担低；React 的 `composition` + `context` 更灵活但容易嵌套过深（"provider 地狱"）。选型时我会先问：团队主用哪个框架？生态成熟度 > 我个人偏好。

### 💥 我踩过的坑

1. **`slot` 滥用导致组件变"大杂烩"**：早期把一个卡片组件啥都用 slot 暴露，结果每个业务页都往里塞完全不同的结构，组件库形同虚设。后来收敛：只暴露"真正会变"的 1–2 个 slot，其余用 props 控制。
2. **全量引 CSS 拖垮首屏**：第一版图省事 `main.ts` 里 `import 'element-plus/dist/index.css'`，打包出来 CSS 多了快 200KB。改成 `unplugin-vue-components` 按需后，UI 相关体积砍了约一半。
3. **props 命名不统一**：有的叫 `onChange`、有的叫 `change`、有的叫 `handleChange`，业务方每次用都要翻源码。定下"事件统一 `update:`/`change`、布尔统一 `isXxx`/`disabled`"的规范后世界清净了。
4. **主题用 `!important` 覆盖**：为了快，业务里直接 `!important` 改组件样式，升级组件版本后样式全崩。正确做法是组件库留 `--css-var` 钩子，业务只改变量不改结构。
5. **版本升级 breaking 没人管**：`major` 一升，下游业务一片红。组件库必须写清 changelog + 提供 codemod/迁移文档，这是对"使用者"的尊重。

### 🎯 面试官可能追问

- 怎么保证组件库不影响业务首屏？（答按需加载 + tree-shaking + 动态 chunk）
- 主题定制怎么做不破坏封装？（答 CSS 变量 + 构建期变量覆盖，业务只改变量）
- 组件库和业务组件怎么划界？（答"零件 vs 套餐"：通用的、跨项目复用的进库；只服务单一业务的留给业务层）
- 怎么让团队愿意用而不是自己重写？（答：文档 + Demo + 真实解决他们痛点 + 别为了"库"而抽库）
- 微前端下组件库怎么共享？（答：抽成独立 npm 包 +  externals 或 module federation，避免多份实例）

> 我不确定之处：React 生态里 CSS-in-JS（如 `styled-components`）在 RSC（React Server Components）下的前途我还没在生产里踩过，理论上它和 Server 渲染有摩擦、社区在往零运行时方案走，但具体迁移坑我得真做一回才知道。

## 大文件分片上传（断点续传 / 秒传）⭐️⭐️⭐️

> 需求：让用户传一个 2GB 的视频。面试官标准三连："网断了怎么办？""同一个人再传一遍呢？""换个人传一样的文件呢？"——这三问就是完整考点。

### 一句话结论

HTTP 的单次请求是为"小而快"设计的；大文件上传的本质，是把"一次大请求必须成功"的不确定性，拆成"多次小请求各自成功"的确定性。核心三件事：**分片**（传输层，切块并发传、按序合）、**断点续传**（状态层，记哪些块成功、只补缺失的）、**秒传**（去重层，用内容指纹命中就建引用、不传内容）。三者共用一个地基：**文件内容指纹**。

### 🍳 生活类比：搬一个顶到天花板的大柜子

你要把一个塞满的大柜子搬上楼。硬扛整个上楼？半路闪了腰（请求超时）、或者绳子断了前面白搬（重传全量）。正确做法：拆成小纸箱（分片），每箱贴"第几箱 / 这一柜子的总编号"（partNumber + fileHash），分批搬；搬一半累了明天接着搬，只补没搬的那些箱（断点续传）；要是邻居家已经有一个一模一样的柜子，直接共享不用搬（秒传）。柜子的"总编号"就是指纹——靠它认出"是不是同一个柜子"。

### 🔍 原理下沉

**1. 切片：`Blob.slice` 不产生内存拷贝**
`File` 继承 `Blob`，自带 `slice(start, end)`，返回的是原文件的一段"视图"，切 2000 片浏览器也不会爆内存。分片大小我习惯 5MB（经验值）；但**别写死常量**——对象存储 OSS / S3 的 Part 有下限（S3 要求 ≥5MB），且 PartNumber 只有 1~10000 个名额，传 100GB 文件必须按 `总大小 / 8000` 动态算，否则超出上限直接废。

**2. 指纹：SparkMD5 增量 + Web Worker**
全量读文件算 MD5 会占 1GB 内存、卡死主线程（进度条不动、按钮点不动都是这个原因）。正确做法：按片增量 `spark.append()` + 放进 Web Worker 算，主线程只管发请求。⚠️ 指纹 key 必须带 `hash + size`——只比哈希等于放弃了一维校验（长度也是内容的一部分）。MD5 只做**完整性 / 去重**，不是防篡改（已被证明可构造碰撞），安全场景用 SHA-256，面试补这句加分。

**3. 秒传：先 check，一次拿两个答案**
上传前发一个 `check` 请求，响应里同时带 `exist`（能否秒传）和 `uploaded`（已传分片序号）。命中就建"用户—文件"引用返回地址，一个字节都不传。
⚠️ 秒传四大坑（面试最爱追）：
- **越权（IDOR）**：只凭哈希命中就返 URL，别人知道哈希就能下你的文件。正确：秒传只去重不做授权，仍按当前用户建独立记录、返回带签名短期 URL。
- **引用计数**：物理文件被多人引用，删除只能删"引用"，归零才删物理文件。
- **绕过审核**：秒传跳过了"上传完成"动作，审核得挂在"文件首次入库"而非"用户上传完成"。
- **跨用户去重复杂度**：中小系统最划算做法是"只做同用户内秒传"（check 带 userId），直接绕开越权 + 引用计数。

**4. 断点续传：filter 已传，只补缺失**
误区：有人以为 HTTP `Range` 请求头能做上传断点——那是**下载**语义（206 Partial Content）。上传没有标准机制，必须"分片 + 状态记录"自己实现。前端拿 `uploaded` 列表过滤掉已传分片，只传缺的；会话用 `uploadId` 而非裸 hash 标识（hash 可能被多人并发传同一文件），临时分片和会话都要带 TTL（建议 24h 起）。

**5. 并发控制 + 幂等**
并发池控 3~5 个，用 `AbortController` 单独重试失败分片不阻塞其他。所有写接口必须幂等：分片按 `uploadId + index` 覆盖写天然幂等；merge 重复调用返回同一结果也要显式做。

### 🔁 对比学习（前端闭环 vs 直传 OSS）

小项目可以前端切片 + 自建三个接口（check / chunk / merge）全自己管；但生产多数直接用对象存储的 **Multipart Upload**（Initiate / UploadPart / Complete / Abort + uploadId），把分片管理、合并、断点能力交给云厂商，前端只做"切片 + 算指纹 + 并发调度"，元数据自己留一份。别依赖 `PUT + Content-Range`（RFC 9110 的 Partial PUT 不要求服务端支持，不支持的服务器会静默把你这片当完整内容覆盖——数据损坏）。

### 💥 我踩过的坑

1. **主线程算 hash 卡 UI**：第一版图省事主线程 `readAsArrayBuffer(file)` 读 1GB，页面冻了三秒，用户以为崩了。挪进 Worker 才顺。
2. **只比 hash 不比 size**：测试时两个不同文件（一个比另一个多了个尾部空字节）哈希不同但被我当成"近似相同"走了秒传，结果内容错乱。加 size 维度后消停。
3. **merge 没校验齐全就合并**：有次前端漏发一片、后端没校验分片数就合并，文件少了一截还返回成功。现在 merge 前必校验"分片数 == 声明总数 + 重算全文件 hash 比对"。
4. **分片大小写死 5MB 传大文件超 PartNumber**：传一个 80GB 的备份，10000 片上限位直接废。动态算分片大小后才解决。

### 🎯 面试官可能追问

- 为什么不能直接传？（请求超时 / 网关限流 / 服务端内存 / 失败全量重传）
- 断点续传是 HTTP Range 吗？（不是，Range 是下载语义）
- 秒传会不会越权？（会，IDOR，必须带 userId + 签名 URL）
- 分片大小怎么定？（对象存储下限 + PartNumber 上限 + 请求数，动态算）
- Web Worker 解决什么？（CPU 密集的 hash 计算不卡主线程）

> 我不确定之处：抽样哈希（只取头尾 + 若干中间片算指纹、秒级出结果）在"超大文件秒传预判"场景的误判率边界，我没在生产压测过，理论上只适合预判不适合当唯一校验——上面是查资料 + 推理，没真踩过。
