### 浏览器渲染流程：解析、重排、重绘、合成（⭐️⭐️⭐️）

**一句话结论：** 浏览器把代码变成屏幕上的像素，要走一条固定流水线：HTML/CSS 解析成 DOM/CSSOM → 合成渲染树 → 布局（重排，算位置尺寸）→ 绘制（重绘，填像素）→ 合成（上 GPU 出图）。**越靠后的步骤越便宜**：只改 `transform`/`opacity` 走合成（最便宜），改几何触发重排（最贵）。面试能讲清这条线和"哪些属性走哪一步"，就够 senior 门槛了。

### 🍳 生活类比

渲染流水线像**给房子装修翻新**：

- DOM + CSSOM = 拿到户型图和材料清单；
- 渲染树 = 决定哪些家具真要摆（把 `display:none` 的踢掉）；
- 布局（重排）= 量每个家具放哪、占多大地方——最费工时；
- 绘制（重绘）= 给墙刷漆、画图案；
- 合成 = 把各层贴一起、拍照出最终图（丢给 GPU，快）。

只想**挪一幅装饰画**（`transform: translateX`），不用重新量房刷漆，直接把那层贴到新位置就行——这就是合成层便宜的原因。但要是**拆墙改尺寸**（改 `width`/`height`），得重排+重绘+合成全来一遍。

### 🔍 原理下沉

关键渲染路径（首屏）：HTML 下载解析建 DOM（增量，预加载扫描器提前要资源）；CSS 是**渲染阻塞**资源——CSSOM 不全浏览器不 paint；JS 同步脚本会阻塞解析（用 `defer`/`async`/`type=module` 解）。DOM + CSSOM 齐了 → 渲染树 → 布局 → 绘制 → 合成。

三个操作的代价阶梯：

| 你改了什么 | 触发 |
|---|---|
| 宽高、位置、字体、增删节点、`top`/`left` | **重排**（布局 → 绘制 → 合成，最贵） |
| 颜色、背景、阴影、`visibility` | **重绘**（跳过布局，仍绘制+合成） |
| `transform`、`opacity` | **仅合成**（GPU，不布局不绘制，最便宜） |

坑点：**强制同步布局（layout thrashing）**——循环里一会儿读 `offsetWidth`（逼浏览器立刻算布局）一会儿写样式，每次读都触发一次重排，几百次重排掉到 60fps 以下。正确做法是**先批量读、再批量写**。

Web Vitals 在这条线上的位置：LCP 在绘制阶段、INP 横跨整条线（JS handler 别堵下一帧 paint）、CLS 在布局阶段（给图片留尺寸别乱挤）。

### 🔁 对比学习（Vue / React 体感）

无论是 Vue 的 `v-if` 切 `display:none`、还是 React 条件渲染卸载节点，本质都是"从真实 DOM 上增删/隐藏元素"，最终都会走这条流水线——所以"用 `transform` 做动画"在框架里一样成立，跟框架无关。

框架的虚拟 DOM diff 再怎么优化，最后落地的还是真实 DOM 操作，该触发重排还是触发。React 的 state 批处理（18 自动批）顺带也减少了"改一次 state 触发一次重排"的 thrashing——和"批量读写"是同一个省性能的思路。

### 💥 我踩过的坑

最实在的一次：早年做列表滚动动画，用 `style.left` 每帧改位置，手机上卡成 PPT。后来才知道改 `left` 每帧都重排，换成 `transform: translateX` 直接走 GPU 合成，丝滑了。这坑现在看到"动画用 left/top"会本能警惕。

还有 layout thrashing：有回循环里 `el.style.width = el.offsetWidth * 2`，读一下写一下，性能工具里紫条（布局）拉满。改成先 `map` 把所有 `offsetWidth` 读出来，再统一写，重排从几百次变成一次。

`will-change` 我也滥用过——给一堆元素标 `will-change: transform` 想提前提层，结果 GPU 内存吃紧反而更卡。现在只给**真会动**的元素标，且动画结束就撤。

### 🎯 面试官可能追问

- 重排和重绘的区别、谁更贵？（重排算几何最贵，重绘只填像素）
- 为什么 `transform` 动画比 `left` 便宜？（只走合成层，不碰布局和绘制主线程）
- 什么是强制同步布局 / layout thrashing？怎么避免？（读写交替逼重排；批量读、批量写）
- LCP / CLS 分别在流水线哪一步优化？（LCP 绘制阶段、CLS 布局阶段）
